# Сравнительный анализ слоёв работы с БД для Boyan (Next-Gen OPDS Suite)

## 1. Специфика базы данных и требования проекта

Для проекта **Boyan (Next-Gen OPDS Suite)** слой работы с базой данных имеет определяющее значение:
1. **СУБД по умолчанию:** **SQLite 3** в режиме `WAL` (Write-Ahead Logging) с драйвером чистого Go (`modernc.org/sqlite`) без CGO.
2. **Полнотекстовый поиск FTS5:** Виртуальные таблицы `books_fts` со стеммингом для русского и английского языков (`tokenize='snowball russian english unicode61'`), поиск по ранжированию `bm25` и триггеры автоматической синхронизации данных при вставке/обновлении книг.
3. **Модель связей «Многие-ко-Многим» с атрибутами:**
   - `Книга` $\leftrightarrow$ `Авторы` (с сохранением порядка соавторов `author_order`).
   - `Книга` $\leftrightarrow$ `Серии` (с хранением дробного/целого индекса книги в цикле `series_index`, например `1`, `2.5`, `3`).
   - `Книга` $\leftrightarrow$ `Файлы форматов` (одна книга может иметь форматы FB2, EPUB и MOBI одновременно с размерами и хешами SHA-256).
4. **Ограничения конкурентности SQLite:** Защита от ошибки `SQLITE_BUSY` (SQLite поддерживает множество одновременных читателей, но только одного писателя).
5. **Потребление RAM:** Бюджет 20–50 МБ на весь процесс сервера.

## 2. Сравнительная матрица вариантов

| Критерий | Вариант 1: `sqlx` + SQL миграции | Вариант 2: `GORM` (`gorm.io/gorm`) | Вариант 3: Чистый `database/sql` | Альтернатива: `sqlc` (Code-gen) |
| :--- | :--- | :--- | :--- | :--- |
| **Уровень абстракции** | Тонкая обертка над `database/sql` с маппингом в структуры | Полноценный ORM (ActiveRecord-паттерн, хуки, автомиграции) | Минимальный (стандартная библиотека) | Генератор типобезопасного Go-кода из чистого SQL |
| **Поддержка SQLite FTS5** | **Идеальная:** чистые SQL-запросы `MATCH ?` и прямой контроль над виртуальными таблицами | **Проблемная:** GORM не понимает виртуальные таблицы без PK, для FTS5 приходится писать `db.Raw()` | **Идеальная:** полный контроль через нативный SQL | **Отличная:** компилирует FTS5 запросы в типы Go |
| **Оверхед по памяти (RAM)** | **Минимальный** (~0.5–1 МБ) | **Высокий** (~5–12 МБ, тяжелая рефлексия, пул хуков, кеш метаданных) | **Абсолютный ноль** | **Абсолютный ноль** (компиляция в нативный Go) |
| **Контроль над транзакциями и WAL** | **Полный:** легкая настройка раздельного пула (1 connection на запись, N на чтение) | Частичный: внутренний Transaction Manager GORM может блокировать пул при сложных связях | **Полный** | **Полный** |
| **Удобство работы со связями (M2M)** | Хорошее: явные JOIN или пакетные выборки через `IN (?)` | Отличное на чтение (`Preload`), но сложное на точечный контроль индексов и триггеров | Низкое: ручной обход `rows.Scan()` для каждой строки | Хорошее: генерирует структуры для JOIN |
| **Автоматические миграции** | Через версионированные файлы `.sql` (embed.FS) — детерминированно и безопасно | Автомиграция структур (`AutoMigrate`), не умеет удалять колонки и ломает FTS-триггеры | Ручное исполнение SQL | Через SQL миграции |
| **Кривая ошибок (Debuggability)** | Ошибки видны в чистом SQL и логах `slog` | Сложный внутренний DSL, скрытые запросы N+1 при неосторожном Preload | Максимальная прозрачность | Максимальная прозрачность |

## 3. Детальный разбор вариантов

### Вариант 1: `sqlx` + Нативные SQL миграции (Рекомендуемый и утвержденный)

`sqlx` расширяет стандартный `database/sql`, добавляя удобный маппинг колонок в поля структур по тегам `db:"title"`, поддержку именованных аргументов (`:title`, `:author`) и срезные выборки `sqlx.Select()`.

#### Преимущества:
1. **Естественная работа с FTS5 и триггерами:** Виртуальная таблица FTS5 создается обычным скриптом миграции `0001_init.up.sql`. Запрос поиска пишется прямо:
   ```sql
   SELECT b.id, b.title, b.annotation, bm25(books_fts) AS rank
   FROM books b
   JOIN books_fts fts ON b.id = fts.rowid
   WHERE books_fts MATCH ?
   ORDER BY rank LIMIT 50;
   ```
2. **Разделение пулов Reader / Writer:**
   В SQLite WAL-режим позволяет иметь неограниченное число параллельных читателей, но строго 1 писателя. С `sqlx` это реализуется кристально чисто:
   - `DB.Writer` (`SetMaxOpenConns(1)`) — для операций парсинга и записи.
   - `DB.Reader` (`SetMaxOpenConns(10)`) — для быстрой отдачи OPDS и REST API.
3. **Прозрачность и производительность:** Никакой неконтролируемой магии рефлексии в рантайме. Идеально укладывается в бюджет памяти 20–50 МБ.
4. **Embed миграции:** Файлы миграций встраиваются прямо в бинарник через `//go:embed migrations/*.sql`. При первом запуске бэкенд сам создает или обновляет схему за доли секунды.

---

### Вариант 2: `GORM` (`gorm.io/gorm`)

GORM — самый популярный ORM в мире Go, реализующий концепцию ActiveRecord.

#### Почему GORM создает серьезные риски для нашего проекта:
1. **Проблемы с FTS5:** В SQLite виртуальные таблицы FTS5 не имеют стандартных первичных ключей (Primary Key) и не поддерживают ряд стандартных операций. GORM пытается валидировать схему, генерирует ошибки на виртуальных таблицах и заставляет разработчика отключать ORM-методы в пользу `db.Raw()`.
2. **Сложность управления связью `Book <-> Series`:** В библиотеках книга входит в серию с определенным номером (`series_index`), часто дробным (например, повесть 1.5). В GORM для Many-to-Many с кастомными атрибутами таблицы связи приходится городить составные модели JoinTable с хуками `BeforeCreate`, что делает код переусложненным.
3. **Оверхед по памяти и CPU:** В GORM активно используется `reflect` на каждый запрос. При индексации библиотеки из 50 000+ книг GORM будет создавать миллионы временных объектов в куче, вызывая частую работу GC и выход за рамки 50 МБ RAM.
4. **Непредсказуемость `AutoMigrate`:** В SQLite операция `ALTER TABLE` имеет жесткие исторические ограничения. Автомигратор GORM в SQLite регулярно падает или блокирует базу при попытке изменить существующие столбцы.

---

### Вариант 3: Чистый `database/sql`

Стандартный драйвер Go без единой сторонней библиотеки.

#### Плюсы:
- Нулевой размер зависимостей.

#### Минусы:
- Огромное количество рутинного кода (boilerplate). Для сущности `Book`, у которой 15 полей, придется в каждом запросе вручную писать:
  ```go
  err := rows.Scan(&b.ID, &b.Title, &b.OriginalTitle, &b.Annotation, &b.Language, ...)
  ```
  Это приводит к человеческим ошибкам при несовпадении порядка полей и снижает скорость разработки в разы.

---

### Вариант 4 (Альтернатива): `sqlc`

Инструмент кодогенерации: разработчик пишет схемы и чистые `.sql` файлы, а `sqlc` на этапе сборки генерирует полностью типобезопасные Go-структуры и методы вызова.

#### Оценка:
Отличный инструмент для продакшена с нулевым рантайм-оверхедом. Однако он требует отдельного CLI-бинарника генератора в процессе сборки.

---

## 4. Сравнительный вывод и утвержденное решение

> [!TIP]
> **Утвержденное решение: `sqlx` + встроенные SQL-миграции (`embed.FS`)**

### Почему этот выбор утвержден:
1. **100% контроль над SQLite WAL и FTS5:** Мы получаем максимум возможностей от полнотекстового поиска SQLite без костылей и ограничений ORM.
2. **Скорость и память:** По скорости не уступает чистому `database/sql`, потребляя считанные килобайты памяти на запрос.
3. **Читаемость:** SQL-запросы каталогизации, многоуровневой сортировки (по авторам, сериям, жанрам) остаются чистым, понятным SQL, который легко оптимизировать через `EXPLAIN QUERY PLAN`.
4. **Надежность миграций:** Четкие версионированные SQL файлы гарантируют стабильность базы данных как на Windows, так и в Linux/WSL2.
