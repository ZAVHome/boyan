# Architectural Rules: Strict Headless & Decoupling

## 1. Headless Backend Constraints
- Бэкенд на Go **НИ ПРИ КАКИХ ОБСТОЯТЕЛЬСТВАХ** не должен содержать серверные HTML шаблоны (никаких `html/template`, Jinja или Bootstrap монолитов).
- Все ответы бэкенда для веб-клиентов должны быть в формате `application/json` (или `image/*`, `application/*` для бинарных файлов книг и обложек).
- Любая функциональность системы должна быть сначала реализована и протестирована на уровне REST API, а затем подключена к фронтенду.

## 2. API Design & Versioning
- Все маршруты API должны начинаться с префикса `/api/v1/`.
- Модели ответов должны быть строго типизированы и содержать аннотации `swag` для автогенерации Swagger документации.
- Пагинация: стандартный формат `{ "items": [...], "total": 1250, "page": 1, "per_page": 50, "total_pages": 25 }`.

## 3. Storage & Concurrency
- SQLite должен работать с `WAL` журналом. Пул соединений для записи должен быть ограничен 1 соединением (`SetMaxOpenConns(1)` при операциях записи) во избежание `SQLITE_BUSY`, в то время как чтение может быть параллельным.
- Для длительных операций (парсинг больших ZIP архивов, пересчёт FTS-индекса) использовать пул фоновых воркеров (Go Worker Pool) с контекстами отмены (`context.Context`).

## 4. Frontend Independence
- Фронтенды (`web-desktop` и `web-mobile`) должны быть полностью работоспособны при размещении на отдельном домене или статическом хостинге (S3/Cloudflare Pages).
- Взаимодействие с API должно быть инкапсулировано в модуль `src/api/client.ts` с использованием сгенерированных TypeScript типов.

## 5. Documentation of Architectural Decisions
- Все сравнительные документы, архитектурные исследования и обоснования решений сохраняются в каталог `docs/decisions/` с обязательным внесением в реестр `docs/decisions/README.md`.
